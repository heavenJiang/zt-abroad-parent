# 选校引擎测试案例（engine-cases）

用已知结果的历史申请案例检验选校引擎。M0-06 由顾问整理 20–30 个案例；M3-08「引擎测试台」批量运行并计算命中率，验收标准为「`seed/engine-cases/` 全部通过」；M6-03 用它校准参数，直到达到创始人设定的命中率（上线门槛，见 `doc/研发/05-开发计划.md`）。

- 模板：`cases_template.csv`（表头 + 3 行虚构示例，`case_id` 以 `EXAMPLE-` 开头）。
- 正式案例：复制模板为 `cases.csv`，删除 3 行示例后填写。测试台跳过所有 `EXAMPLE-` 开头的行。
- 参数：`seed/engine-config/`；说明与算例：`doc/准备/M0-06-引擎参数草案说明.md`。

## 1. 一行 = 一个学生申请一个项目

同一学生申请了 5 个项目就写 5 行，用同一个 `student_ref` 关联。一行包含三部分：**学生背景**（与测评问卷同一套维度）、**这次申请**（国家、学校、项目、入学季）、**结果与顾问判断**（实际结果、顾问认为当时应属的档位）。

### 列说明

文件为 UTF-8、逗号分隔、首行表头、标准 CSV 引号规则（与 `seed/cn-university` 一致）。用 Excel 填写时“另存为 → CSV UTF-8”，导入程序需兼容带 BOM 的文件。可选项不知道就留空，不要填 0。

列名和取值与问卷归一化后的档案字段一致（`seed/questionnaire`，M0-04），测试台可以直接把一行当作一份档案喂给引擎。

| 列 | 必填 | 取值 / 说明 |
| --- | --- | --- |
| `case_id` | 是 | 案例编号，如 `UK-001`；示例行以 `EXAMPLE-` 开头 |
| `student_ref` | 是 | 匿名学生编号，如 `S-0007`；**不得**用姓名、拼音、学号、手机号或可反推身份的编号 |
| `verification_level` | 是 | `A` 顾问核验 offer / `B` 有截图 / `C` 只有自报（与《模块详细设计》案例库一致）。D 级（论坛等未核验）不得放入 |
| `intake` | 是 | 入学年月 `yyyy-MM`，如 `2025-09` |
| `country` | 是 | `US` `UK` `AU` `SG` `JP` `KR` `DE` |
| `degree` | 是 | 本批只收 `master` |
| `target_field_group` | 是 | 专业大类：`business` `stem` `health` `humanities_social` `arts`（与问卷 `target_field` 的分组一致） |
| `target_school` / `target_program` | 是 | 申请的学校与项目全称（项目库录入后按项目库名称归一） |
| `program_difficulty` | 是 | 顾问给该项目定的难度档 `D1`–`D5`（定义见各国 JSON 的 `benchmark_defaults`）；项目库里已有参考线时以项目库为准，本列用于项目尚未录入时 |
| `teaching_language` | 是 | `en` `ja` `ko` `de` 等 |
| `application_path` | 日本必填 | `direct_master` 直申修士 / `research_student` 研究生（预科） |
| `undergrad_tier` | 是 | `c9` `985` `211` `double_first_class` `non_key`（双非）`overseas`（海本）。**只写层次，不写本科校名** |
| `major_relevance` | 是 | `same` 本专业 / `related` 相近 / `cross` 跨专业 |
| `missing_prereq_count` | 否 | 缺少的先修课门数 |
| `gpa_raw` / `gpa_scale` | 是 | 原始均分与满分，如 `85`/`100`、`3.6`/`4` |
| `gpa_percent` | 否 | 已换算的百分制；留空则按问卷的换算表换算 |
| `class_rank` | 否 | `top10` `top30` `other`；不知道留空 |
| `english_test` / `english_total` / `english_min_sub` | 是 | `ielts` `toefl` `pte` `duolingo` `none`，申请时的总分与最低小分 |
| `ielts_equiv_total` / `ielts_equiv_min_sub` | 否 | 雅思等效分；留空则按问卷的对照表换算 |
| `jlpt_level` / `topik_level` | 日 / 韩语项目必填 | `N1` `N2` `N3` `N4_N5` / `1`–`6` |
| `std_test_type` / `std_test_total` | 否 | `gre` `gmat_focus` `gmat_classic` 与总分；没考留空 |
| `research_level` / `research_count` / `research_relevant` | 是 | 最高级别 `core_journal` `conference` `lab_project` `none`；段数；是否与申请专业相关 `yes` / `no` |
| `work_months` / `work_fulltime_months` / `work_company_tier` / `work_relevant` | 是 | 实习 + 工作累计月数（无则 0）；其中全职月数；`top` 有头部公司经历 / `normal`；`yes` / `no` |
| `awards_level` / `awards_count` | 是 | 竞赛、项目、证书的最高级别 `international` `national` `provincial` `school` `none`；项数 |
| `course_match_ratio` | 德国必填 | 已对口学分 / 项目要求学分，0–1 |
| `de_aps_status` | 德国必填 | `passed` `in_progress` `not_started`（以申请时状态为准） |
| `scholarship_applied` | 韩国选填 | `Y` / `N` |
| `pre_sessional_offered` | 否 | 是否拿到“读语言班”的有条件录取，`Y` / `N` |
| `outcome` | 是 | 实际结果 `admit` / `reject` / `waitlist`。有条件录取记 `admit`；撤申的案例不收 |
| `waitlist_final` | 候补时填 | 候补的最终结果 `admit` / `reject`；仍未知留空 |
| `consultant_tier` | 是 | 顾问认为**以申请时的背景**这个项目应属的档位：`冲` / `稳` / `保`（不是看了结果之后的判断） |
| `is_borderline` | 是 | `Y` / `N`：顾问自己也拿不准、或结果出乎意料的案例 |
| `consultant_note` | 否 | 简短理由，如“均分刚过分层线”“面试表现好”。不得写任何能识别学生的信息 |

背景字段一律填**申请时**的情况（如申请时雅思 6.5、后来考到 7.0，写 6.5）。

## 2. 脱敏

- 只用匿名编号（`case_id`、`student_ref`），不出现姓名、手机号、微信号、证件号、邮箱、学号。
- 本科学校只写层次 `undergrad_tier`；不写本科校名、班级、导师名、实习公司名、论文题目（只写级别、段数与是否相关）。
- 对照表（匿名编号 ↔ 真实学生）不放入本仓库，由工作室内部保管。
- 只放已获得「算法使用授权」的案例（案例库规则：宣传授权与算法授权分开）。顾问在前公司经手的案例，只能在不违反保密义务的前提下以脱敏特征写入；不能确定时不要放。
- 小众组合（如某个冷门项目全年只录一位学生）即使脱敏也可能被认出：在备注中写“小样本”，测试台只在管理端展示。

## 3. 什么样的测试集算好

**数量与分布（20–30 个）**：每个国家都要有**录取、拒绝、边界**三类（开发规范 14.4：每国正、反、边界三类样例）。建议：

| 国家 | 建议条数 | 至少包含 |
| --- | --- | --- |
| 英国、澳洲、新加坡（第 1 批上线） | 各 4–6 | 录取 ≥ 2、拒绝 ≥ 1、边界（`is_borderline=Y` 或候补）≥ 1 |
| 美国（第 2 批） | 3–5 | 商科与理工各至少 1 条；录取、拒绝、边界各 ≥ 1 |
| 日本、韩国、德国（第 3 批） | 各 3 | 录取、拒绝、边界各 1；日本两种路径都要有，德国要有课程匹配度偏低的案例 |

某国一个案例都凑不齐时，说明该国暂不具备上线条件：在说明文档中标注“该国未覆盖”，该国配置保持 `draft`，不要用虚构案例凑数。

**质量要求**：

1. **拒绝和候补与录取同样重要**。只收录取会让引擎看起来全对、实际系统性高估。
2. **覆盖不同难度和背景**：D1–D5 各档、c9 到 non_key（双非）各层次都要有；不要全是“好学生申好学校”。
3. **三档都要有**：`consultant_tier` 中冲、稳、保都要出现，否则无法算每档命中率。
4. **近期**：优先近 2–3 个申请季；政策变化大的项目（均分线、语言要求改过）在备注注明。
5. **可核验**：优先 A、B 级；C 级可以放，但统计时单独列出。
6. **同一学生不超过 5 行**，避免一个学生的背景主导整个测试集。
7. **边界案例要真**：`is_borderline=Y` 用于“顾问当时也不确定”或“结果和预期相反”，这类案例最能暴露参考线和稳定度 a 的问题。

## 4. 命中率怎么算

测试台对每一行用当前配置版本计算：硬门槛 → 综合分 C → P → 引擎档位。之后按下列口径统计（P 只在测试台显示，不出现在学生端）。

**先排除**：`EXAMPLE-` 行；硬门槛判为「补足后可申」的行单独列出（不进档位统计），若这类行实际被录取，记为**硬门槛误判**，需逐条复核。

**① 档位命中率（主指标，对应「每档命中率」）**

```
某档命中率 = 引擎档位 = 顾问档位 = 该档 的行数 ÷ 顾问档位 = 该档 的行数
整体命中率 = 引擎档位与顾问档位一致的行数 ÷ 参与统计的行数
```

同时输出 3×3 混淆矩阵（行：顾问档位，列：引擎档位）。

**② 严重错档**：引擎与顾问相差两档（冲 ↔ 保）的行数。这类错误最伤学生信任，目标通常是 0。

**③ 结果一致性（辅助指标）**：按引擎档位分组，算实际录取率。`admit` 计 1，`reject` 计 0，`waitlist` 按 `waitlist_final` 计，最终结果未知的不计。期望：保 > 70%、稳 35%–70%、冲 < 35%（§4 阈值）。每组少于 10 行时只显示“样本不足，仅供参考”，不作为是否上线的依据。

**示例**（虚构数字）：24 行参与统计，顾问档位冲 6 / 稳 12 / 保 6；引擎与顾问一致的分别为 4、9、5。

```
冲 4/6 = 66.7%   稳 9/12 = 75.0%   保 5/6 = 83.3%   整体 18/24 = 75.0%
```

若另有 1 行顾问判“保”、引擎判“冲”，则严重错档 = 1。

结果按国家和整体分别输出，并列出每一条不一致案例（`case_id`、引擎档位、顾问档位、C、T 及其来源、P），供 M6-03 逐条分析。

## 5. 维护

- 改权重、参考线或公式后，重新跑全部案例并在说明文档记录前后命中率（开发规范 14.4：改权重或公式时同步更新样例）。
- 上线后，签约学生的录取结果按服务流程回流案例库；本目录只保留用于回归测试的固定集合，新增案例按季度评审后再加入。
