# 熔断演练（M10-03）

## 目的

验证获客自动化的安全阀在真实链路上有效：模拟**退订激增、投诉、平台违规提示**，确认熔断规则会自动暂停对应 Agent / 渠道账号 / 全部获客自动化，写熔断记录、通知有暂停权限的员工，暂停后发送被拦下，恢复后状态正常。

## 怎么跑

脚本 `deploy/drill/breaker-drill.sh`，只调用接口（不直接改数据库），**只在测试环境运行**：

```bash
BASE=http://测试环境后端:8090 APP_URL=https://测试环境C端域名/ TOKEN=<管理员令牌> deploy/drill/breaker-drill.sh
```

- 前置条件：消息渠道为 mock（`ABR_CHANNEL_MOCK=true`）、服务号登录为 mock（`ABR_WECHAT_OA_MOCK=true`），获客自动化与演练用的两个 Agent 当前未暂停；不满足时脚本拒绝执行。
- `TOKEN` 为管理员登录后浏览器中的 `Admin-Token`；可用 `UNSUB_AGENT`（默认 booking_agent）、`COMPLAINT_AGENT`（默认 nurture_agent）、`USERS`（默认 14）、`WAIT`（每项最多等待秒数，默认 180）调整。
- C 端登录按 IP 限流（每分钟 10 次），脚本每建一个演练账号等 7 秒，整个演练约 5 分钟。
- 演练结束时恢复全局与两个 Agent、删除演练模板（`drill_marketing`）与演练账号（`drill_acc`）；演练用的 C 端账号（渠道码 `drill`）、触达、退订与信号记录保留，便于复盘。重复演练时退订人数按窗口内已有的营销触达自动计算。
- 输出逐项结果并写入报告文件（`REPORT`，默认当前目录 `breaker-drill-时间.md`），全部通过时退出码为 0。

## 场景与验证点

| 场景 | 做法 | 预期 |
| --- | --- | --- |
| 退订激增 | 给 14 个演练账号各发 3 条营销消息（mock 渠道），其中若干人在 C 端退订，使该 Agent 24 小时退订率 ≥ 5%（至少 40 条） | 该 Agent 被熔断暂停、有熔断记录、员工收到提醒、暂停后再发被拦下；恢复后对已退订的人（按学生账号发送）仍被拦下 |
| 投诉 | 对一个 Agent 登记 2 条投诉 | 该 Agent 被熔断暂停、有熔断记录 |
| 平台违规提示 | 对演练账号登记 1 条平台违规提示 | 账号被暂停、全部获客自动化被全局暂停、任何 Agent 的发送被拦下 |

## 演练发现并已修复的问题

- **退订只记在访客上**：学生在 C 端退订营销消息时退订记在访客身份上，而对同一个人按学生账号或线索发的营销消息仍会发出；退订信号也只按发给访客的触达归因，熔断的退订率统计不到这些消息。已改为**按人**：同一人的访客、学生账号、线索任一退订即视为退订，退订归因与每周营销触达上限（频控）也按人合计（`AbrTouchLogMapper` 的 `personIdentities`）。
- 演练脚本自身的问题（C 端登录限流、登录后访客令牌失效改用学生令牌、暂停与熔断记录写入的先后）已在脚本中处理。
